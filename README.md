# Blog REST API

A small Go API with SQLite persistence. A `Blog` represents one blog post.
Users author posts and comments. Tags have a many-to-many relationship with posts
through the `blog_tags` table.

## Development

Requires Go 1.24.2 or newer. No separate database server or C compiler is needed.

```sh
make dev
```

The server listens at `http://127.0.0.1:8080`. It creates `data/blog.db` and applies
the embedded schema migration on startup. Data survives server restarts.

`make dev` runs [Air](https://github.com/air-verse/air) at a pinned Go 1.24-compatible
version. The first run downloads the tool; no global installation is needed.
Changes to Go source, embedded `.sql` files, `go.mod`, and `go.sum` rebuild and
restart the API after a 300 ms debounce. Test files, the frontend, SQLite data,
editor files, and generated binaries are excluded from the watcher.

Air sends an interrupt for graceful shutdown and allows two seconds before forcing
the old process to exit. Build failures appear in the terminal and stop the API;
fixing the code starts it again. A build failure summary is also saved under `.air/`.
Ctrl+C stops the watcher and API. Temporary binaries are cleaned up on exit.

API restarts disconnect WebSockets. The Svelte frontend reconnects automatically.
Each restart resets the in-memory chat history; SQLite blog data persists.
Rebuilding embedded SQL does not reapply an already-completed schema migration.

For a single run without watching, use `make run`. Build a standalone server with
`make build` and run `./bin/api`.

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `ADDR` | `127.0.0.1:8080` | HTTP listen address |
| `DB_PATH` | `data/blog.db` | SQLite file path; `:memory:` for temporary data |

```sh
ADDR=127.0.0.1:9000 DB_PATH=data/development.db make dev
```

This base implements resource management. Users are author records; authentication
and authorization are not implemented. The default address accepts local connections.

## Routes

Each resource supports these operations:

| Method | Route | Result |
| --- | --- | --- |
| `GET` | `/users`, `/blogs`, `/comments`, `/tags` | List resources (`200`) |
| `POST` | same collection routes | Create a resource (`201`, with `Location`) |
| `GET` | `/{resource}/{id}` | Read a resource (`200`) |
| `PUT` | `/{resource}/{id}` | Replace writable fields (`200`) |
| `DELETE` | `/{resource}/{id}` | Delete a resource (`204`) |
| `GET` | `/health` | Database connectivity (`200` or `503`) |
| `GET` | `/ws` | Upgrade to a WebSocket connection (`101`) |

Collection responses are JSON arrays ordered by ascending ID. Empty results are
`[]`. Use `?limit=20&offset=0` for pagination. The default limit is 20, maximum 100;
offset must be between 0 and 1,000,000.

- `/blogs?tag_id=1` filters posts by tag.
- `/comments?blog_id=1` filters comments by post.
- IDs and filter IDs must be positive integers. A valid filter with no matches returns `[]`.

## Write payloads

Send `Content-Type: application/json` for `POST` and `PUT`. Unknown fields are
rejected. IDs and timestamps are generated by the server and cannot be written.

| Resource | Writable fields | Validation |
| --- | --- | --- |
| User | `name`, `email` | Name: 1–100 characters; valid email, at most 254 bytes |
| Blog | `title`, `body`, `author_id`, `tag_ids` | Title: 1–200; body: 1–100,000 characters; existing author; at most 100 unique existing tags |
| Comment | `blog_id`, `author_id`, `body` | Existing post and author; body: 1–10,000 characters |
| Tag | `name` | 1–50 characters; unique without regard to ASCII case |

Text is trimmed. Email addresses are trimmed and lowercased; email uniqueness is
case-insensitive. Tag names preserve their casing. SQLite's built-in case folding
for uniqueness is ASCII. Each request body is limited to 1 MiB.

`PUT` replaces all writable fields. Omitting `tag_ids`, sending `null`, or sending
`[]` clears the post's tags. Other fields are required for both creation and replacement.
Blog responses include a `tags` array of `{ "id": 1, "name": "Go" }` objects.
Timestamps use UTC RFC 3339 strings.

## Try it

With a fresh database, run these commands in order:

```sh
curl -i http://127.0.0.1:8080/users \
  -H 'Content-Type: application/json' \
  -d '{"name":"Ada","email":"ada@example.com"}'

curl -i http://127.0.0.1:8080/tags \
  -H 'Content-Type: application/json' \
  -d '{"name":"Go"}'

curl -i http://127.0.0.1:8080/blogs \
  -H 'Content-Type: application/json' \
  -d '{"title":"First post","body":"Hello, world!","author_id":1,"tag_ids":[1]}'

curl -i http://127.0.0.1:8080/comments \
  -H 'Content-Type: application/json' \
  -d '{"blog_id":1,"author_id":1,"body":"Nice post."}'

curl 'http://127.0.0.1:8080/blogs?tag_id=1'
curl 'http://127.0.0.1:8080/comments?blog_id=1'
```

Use returned IDs if the database already contains data.

## Svelte chatroom

The `frontend/` package is a Svelte 5 chatroom. Every connection joins one shared
conversation. It includes display names, message bubbles, a composer, connection
status, and automatic reconnection.

With Node 24 installed, start the API in one terminal:

```sh
make dev
```

In a second terminal:

```sh
npm --prefix frontend ci
make frontend
```

Open [the chatroom](http://127.0.0.1:5173) in two tabs, choose display names, and
send a message. Both tabs receive it, including the sender. Enter sends a message;
Shift+Enter adds a new line. Vite proxies `/ws` to the local API.

Run `make frontend-test` and `make frontend-build` to verify the package. See
[frontend/README.md](frontend/README.md) for configuration and deployment details.

## WebSocket chat and updates

Connect to `ws://127.0.0.1:8080/ws` (`wss://` when using HTTPS). This is a standard
WebSocket endpoint. On connection, the server sends a `ready` message with a
`client_id` and a `history` array containing up to 100 recent chat messages. The
history field is omitted when the conversation is empty.

Send a chat message:

```json
{ "type": "chat", "name": "Ada", "message": "Hello everyone!" }
```

Every connected client, including the sender, receives the same message:

```json
{
  "type": "chat",
  "id": 1,
  "client_id": 7,
  "name": "Ada",
  "message": "Hello everyone!",
  "timestamp": "2026-10-21T15:00:00Z"
}
```

The API assigns IDs, connection identity, and timestamps. Clients cannot supply
these fields. Names and messages are trimmed. Names allow at most 40 Unicode
characters; an empty name becomes `Guest {client_id}`. Messages require 1–500
Unicode characters. Invalid messages produce a private error reply to the sender.
Display names are freely chosen and do not identify authenticated users.

One shared hub broadcasts all chat and REST change events. Simultaneous chat
messages have the same order for every recipient. The server keeps the latest
100 chat messages in memory and sends a snapshot before live events on each
connection. Chat history resets when the API restarts and is not stored in SQLite.

Successful REST creates, updates, and deletes still broadcast JSON notifications:

```json
{
  "type": "created",
  "resource": "blogs",
  "id": 1,
  "timestamp": "2026-10-21T15:00:00Z"
}
```

- `type`: `created`, `updated`, or `deleted`.
- `resource`: `users`, `blogs`, `comments`, or `tags`.
- `id`: the changed resource's ID. Fetch the resource through REST for its content.
- `timestamp`: the notification's UTC RFC 3339 time.

Failed writes and reads emit no change event. A deletion emits one event for the
requested resource; cascading comment deletions and tag-link changes do not emit
separate events. Refresh related data when a post or tag changes.

Clients can send `{"type":"ping"}` and receive `{"type":"pong","timestamp":"..."}`.
Unsupported or malformed JSON receives `{"type":"error","message":"...","timestamp":"..."}`.
Socket messages do not write to the database. Use REST for blog resource mutations.

Example for a browser page served from the API's origin:

```js
const url = new URL("/ws", window.location.href);
url.protocol = window.location.protocol === "https:" ? "wss:" : "ws:";
const socket = new WebSocket(url);

socket.onmessage = ({ data }) => {
  const event = JSON.parse(data);
  if (event.type === "ready") {
    // Fetch the initial state through REST. Repeat after each reconnect.
    console.log("Connected");
  } else if (event.type === "chat") {
    console.log(event.name, event.message);
  } else if (event.resource) {
    // Refetch affected lists or records through REST.
    console.log(event.type, event.resource, event.id);
  }
};

socket.onopen = () => socket.send(JSON.stringify({ type: "ping" }));
```

Browser connections must have an Origin host and port matching the API. Non-browser
clients may omit Origin. There is no authentication or subscription filtering;
all connected clients receive all chat messages and change notifications.

The server sends protocol heartbeat pings every 25 seconds and disconnects clients
that have not sent a protocol pong for 60 seconds. Browser WebSocket clients handle
these control frames automatically. Incoming messages must be UTF-8 JSON text and
no larger than 4 KiB. Binary and oversized messages close the connection.

Each connection has a 64-message outgoing queue. A full queue disconnects that
client so it cannot hold up REST writes or other clients. The shared room is local
to one API process. Reconnecting clients receive the latest 100 chat messages;
older messages are not replayed. REST change notifications have no replay, so
clients should refetch resource state after reconnecting. Server shutdown closes
active sockets with WebSocket code `1001`.

### Socket logs

The API writes socket activity through its `slog` logger. The default server prints
logs to stderr, including the terminal running `make dev` or `make run`.

- INFO: connected clients, incoming data messages, and disconnections.
- WARN: rejected handshakes and invalid or unsupported messages.
- Each connection attempt gets a process-local `connection_id`. Logs also include
  `component=websocket` and the TCP peer's `remote_addr`.
- Incoming messages include `frame_type`, `bytes`, and the text `payload` when it
  is valid UTF-8. Payloads remain bounded by the 4 KiB incoming-message limit.
- Disconnections include `reason`, `duration`, `messages_received`, and the peer's
  WebSocket close code when available. Reasons include shutdown and a full queue.

For example, sending `{"type":"ping"}` produces an API log like:

```text
INFO socket message received component=websocket connection_id=1 remote_addr=127.0.0.1:54321 frame_type=text bytes=15 payload="{\"type\":\"ping\"}"
```

## Errors and relationships

Errors use `{ "error": "message" }`:

| Status | Meaning |
| --- | --- |
| `400` | Invalid JSON, fields, IDs, or pagination |
| `404` | Resource or route does not exist |
| `405` | Method not supported; `Allow` lists supported methods |
| `409` | Duplicate email/tag, missing referenced resource, or user still has content |
| `413` | Request exceeds 1 MiB |
| `415` | Missing or unsupported `Content-Type` |
| `500` | Unexpected server error; details stay in server logs |

- Deleting a post deletes its comments and tag assignments.
- Deleting a tag removes its assignments and preserves the posts.
- Deleting a user with posts or comments returns `409`. Delete or reassign their content first.
- Post creation/replacement and tag assignment commit together or roll back together.
- Foreign keys, unique values, and text length constraints are enforced by SQLite.

## Test and build

```sh
make test   # Tests against real SQLite, with race detection and coverage
make check  # go vet and formatting check
make build  # Produces bin/api
```

The tests cover all CRUD routes, normalization and validation, JSON errors,
pagination, filtering, uniqueness, foreign keys, cascading deletes, transaction
rollback, concurrent writes, persistence across reopen, and schema migration failure.
WebSocket tests cover multi-client broadcasts, failed writes, message validation,
origin checks, size limits, slow-client handling, concurrency, and shutdown. Chat
tests cover universal broadcasts, shared ordering, history limits, late joins,
Unicode validation, and rejection of forged identity fields.
Each test gets an isolated database. Tests do not use `data/blog.db`.

GitHub Actions runs checks, tests, and builds on pushes and pull requests.

## Layout

```text
cmd/api/                Server entry point and graceful shutdown
internal/api/           HTTP/WebSocket routes, validation, connection hub, tests
internal/model/         Resource models and write payloads
internal/store/         SQLite queries, embedded schema, database tests
frontend/               Svelte chatroom, Vite proxy, frontend tests
```

SQL uses bound parameters. SQLite uses WAL for file databases, a five-second busy
timeout, and one connection per process to serialize local writes. Schema version
1 is recorded in `PRAGMA user_version`; future migrations belong in `internal/store`.

The SQLite driver is pinned to a Go 1.24-compatible version. Driver documentation:
[modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite).
WebSocket driver documentation:
[gorilla/websocket](https://pkg.go.dev/github.com/gorilla/websocket).
